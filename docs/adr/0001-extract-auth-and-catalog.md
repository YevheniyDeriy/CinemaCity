# ADR-0001. Виділити Auth і Catalog із моноліту CinemaCity

## Статус

Accepted — 2026-10-15.

## Контекст

Вихідний CinemaCity має один API і PostgreSQL: користувачі, JWT, каталог фільмів та серіалів, сезони, акторський склад, TMDb-імпорт, оцінки, рецензії та списки. [Інвентаризація](../inventory.md) показує, що персональні функції поєднують ідентичність, метадані та активність. У локальній вихідній БД до переходу було 221 фільм/серіал, 8 користувачів, 5 епізодів і 3 рецензії. Це не каталог сторонніх Item/Category.

## Розглянуті варіанти

1. Залишити моноліт і виділити лише Auth. Менше змін, але не виконується незалежне володіння каталогом і вимога ЛР1.
2. Auth + один великий доменний сервіс із каталогом, рецензіями й профілями. Простіші локальні запити, але метадані та активність користувачів залишаються одним deploy і сховищем.
3. Auth + Catalog + залишок Community у моноліті. Межі відповідають бізнес-можливостям; доводиться явно розв'язати залежності персональних функцій від каталогу.

## Рішення

Обрано третій варіант. Auth володіє користувачами, ролями й сесіями. Catalog володіє вихідними Movie/Genre/Country/Language/Person/Cast/Season/Episode та імпортом. Community зберігає оцінки, рецензії, коментарі, списки та рекомендації. Нові сервіси мають власні моделі, контексти й міграції; вони не посилаються на Domain/Application/Infrastructure моноліту або один на одного. Shared містить тільки технічні налаштування.

Дані переносяться одноразовою offline-утилітою, із збереженням UUID, хешів паролів і зв'язків. Утиліта читає джерело в read-only repeatable-read транзакції та відмовляється перезаписувати непорожню ціль без маркера імпорту. Повторний запуск не скидає зміни сервісів. Runtime не отримує connection string чужої БД.

Community підтримує у власній БД `projections` для старих запитів, персональних списків та локальних FK. Ці таблиці — кеш API-снапшотів, а не друге джерело істини. Вихідний стан перед переходом заархівований у `legacy`; перед переходом створюється pg_dump backup. Поточні зміни користувачів та каталогу виконують тільки відповідні власники.

## Наслідки

- Зберігаються оригінальні UI, користувачі, фільми, рецензії та зв'язки; не з'являється паралельний демонстраційний застосунок.
- Каталог і автентифікація незалежно збираються, запускаються та перевіряють JWT локально.
- Перевірки UserId/MovieId, власні оцінки епізоду та перевірка оцінених епізодів при імпорті стають HTTP-викликами, переліченими в інвентаризації.
- Відмовляємося від спільної транзакції оцінки та агрегату Catalog. Локальний outbox із повторною доставкою та версією дає eventual consistency.
- Проєкції можуть відставати до наступного оновлення; перед операціями з конкретним ID виконується адресне оновлення. Для широких читань повне оновлення обмежено інтервалом 5 секунд. Якщо власник недоступний, новий запит, якому потрібна актуалізація, отримує 503; збережені оцінки залишаються в БД.
- Зростає кількість процесів, міграцій, контрактів і сценаріїв перевірки. Видалені метадані в локальній історичній проєкції можуть залишатися для старих посилань; це не право моноліту змінювати каталог.
