# ADR-0004: розширення шлюзу для екрана фільму

Статус: прийнято. Дата: 2026-10-29.

Контекст: клієнт потребує публічного опису фільму Catalog і персональної оцінки/списків Community. Моноліт змінювати заборонено. Створення оцінки, перевірки її допустимості та розрахунок рейтингу залишаються в сервісах.

Рішення: GET /api/v1/screens/movies/{id} з окремим DTO шлюзу; Task.WhenAll для двох HTTP-викликів; головний Catalog обов'язковий, Community може явно дати partial response. Окремий IScreenComposer дозволяє додавати екрани без редагування MovieScreenComposer.

Для автентифікації обрано локальну перевірку JWT на вході та передачу токена вниз; чужі identity-заголовки видаляються. Перевірки сервісів залишені як defense in depth. Варіант довірених X-User-Id відхилено, щоб не створити залежності безпеки від локальних діагностичних запусків. У Docker сервісні порти не публікуються.

IMemoryCache зберігає лише анонімно отриманий публічні деталі фільму для екрана, TTL 60 с. Ключ включає канонічний path з UUID та покоління. Звичайні проксовані API-відповіді зі статистикою оцінок не кешуються, щоб не змінити їхню поведінку з ЛР2. Після успішної зміни каталогу через шлюз змінюється покоління до повернення відповіді. Альтернативу кешувати весь екран відхилено: він містить персональні дані.

Fixed window з розділенням login/IP, anonymous/IP та authenticated/sub; 429 ProblemDetails з Retry-After. Всі downstream мають дедлайн 3 с, помилки явно позначаються. Liveness відокремлений від readiness сусідів.

Наслідки: один клієнтський запит збирає екран, загальні дані кешуються без ризику змішування користувачів. Кеш локальний для одного gateway; для кількох реплік знадобиться спільна інвалідизація та розподілений limiter. Зміни каталогу в обхід gateway видно після TTL. Відповідь 401 шлюзу стала ProblemDetails за вимогою ЛР3; бізнес-контракти не переносилися в gateway.
