# ADR-0002. Єдина зовнішня адреса CinemaCity через Ocelot

## Статус

Accepted — 2026-10-15.

## Контекст

Існуючий React frontend використовує `/api/auth`, `/api/movies`, `/api/admin/...`, `/api/profile` та публічні профілі. Виділення сервісів не повинно змушувати користувача переходити в іншу програму. ЛР0 вимагає спочатку прозорий gateway перед монолітом; ЛР1 — перемикання Auth/Catalog.

## Розглянуті варіанти

1. Без шлюзу: frontend знає три адреси. Кожне виділення потребує зміни клієнта; CORS і діагностика розпорошені.
2. Ocelot: JSON-маршрути, явні пріоритети, конфігурація downstream і middleware ASP.NET. Додається окремий процес і залежність від пакета.
3. YARP: гнучке проксування на ASP.NET, але для навчального завдання потрібен саме Ocelot; гнучкість не виправдовує відхилення від умов.
4. Хмарний gateway: зручна керована інфраструктура, але зовнішній акаунт, мережа й додаткові витрати не потрібні для локального CinemaCity.

## Рішення

Використати окремий Ocelot на 5000. `Gateway:Mode=Monolith` направляє всі маршрути на моноліт 5100 без переписування шляху. `Mode=Services` перемикає Auth на 5001, Catalog на 5002, а персональні функції залишає в моноліті. Хости, порти, режим та файл маршрутів читаються з конфігурації; Docker задає імена контейнерів через environment.

Публічний контракт сервісів — `/api/v1`. Старі шляхи UI залишаються alias на gateway: наприклад, `/api/movies/{id}` → `/api/v1/catalog/movies/{id}`. У `/api/users` адміністративні `me`, список і `roles` спрямовані до Auth, а публічні профілі/списки/рецензії — до Community через catch-all.

Явні маршрути записані перед catch-all та мають вищий `Priority`; catch-all має 0. Пріоритет задається явно, а не покладається лише на фізичний порядок JSON. `/health` обробляється middleware до термінального Ocelot, тому gateway не містить контролерів чи бізнес-логіки. Кожен запит має X-Correlation-Id; записуються метод, шлях без query, отримувач, статус і тривалість. Секрети та тіла запитів не журналюються. При недоступному downstream клієнт отримує 503 ProblemDetails, а health gateway залишається 200.

## Наслідки

- Frontend залишається тим самим CinemaCity; після першого переведення його базової адреси на gateway нове розміщення API приховане від клієнта.
- Можна окремо показати стан ЛР0 та після ЛР1 й перевірити вибір маршруту, не змінюючи доменну модель.
- З'являється додатковий мережевий перехід і потенційна точка відмови. Liveness gateway не означає, що всі його downstream готові: їхні health перевіряються окремо.
- Потрібно підтримувати карту legacy alias; неоднозначні `/api/users` мають окремі явні правила.
- Вебклієнт потребує CORS на gateway; для uploaded assets Vite/nginx також направляє `/uploads` на gateway.

Посилання на реалізаційні правила: [Ocelot routing](https://ocelot.readthedocs.io/en/latest/features/routing.html), [terminal pipeline](https://ocelot.readthedocs.io/en/latest/introduction/gettingstarted.html).
