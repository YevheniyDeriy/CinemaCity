# Контрольні питання й пояснення для захисту

## ЛР0

1. **API Gateway** приймає зовнішні HTTP-запити та вибирає внутрішній застосунок. У CinemaCity він відповідає за маршрутизацію, CORS, correlation ID, технічні логи та зрозумілу помилку недоступності. Він не містить каталожної чи користувацької бізнес-логіки й не працює з БД.
2. **Strangler Fig:** спочатку клієнта переводять на стабільну зовнішню адресу. Потім власників окремих маршрутів можна змінювати за gateway. Для цього в нас є режими Monolith і Services.
3. **Upstream** — шлях клієнта до gateway, наприклад `/api/movies/{id}`. **Downstream** — власник і його шлях: `Catalog :5002 /api/v1/catalog/movies/{id}`.
4. **Catch-all і порядок:** явні маршрути розташовані перед catch-all. У використаній версії Ocelot вибір додатково зафіксований `Priority`: конкретні правила мають 100/150/200, загальне — 0. Не варто покладатися тільки на порядок рядків; помилковий пріоритет може спрямувати запит до моноліту.
5. **UseOcelot** — термінальний pipeline. Health реалізовано middleware, яке завершує `/health` до виклику Ocelot; додавати після нього звичайні обробники не потрібно.
6. **ADR:** запис одного рішення. Обов'язкові заголовок/номер, статус, контекст, варіанти, рішення, наслідки.
7. **Мінуси в наслідках** фіксують ціну вибору: додаткові процеси, мережа, eventual consistency, підтримка контрактів і проєкцій.
8. **Композиція** показує процеси, порти, сховища та зв'язки. **Послідовність** показує один сценарій у часі, включно з перевіркою JWT та відповідями.
9. **Протокол на стрілці** дозволяє відрізнити локальну роботу з власною БД від HTTP-виклику іншого процесу. Мережева взаємодія має таймаути та окремі відмови.
10. **Перемикання ЛР1:** адреси Auth/Catalog у downstream більше не вказують на моноліт; з'являються власні порти 5001/5002. У нашій конфігурації це `Gateway:Mode` плюс `Services:*Url`, а alias також зберігають оригінальні шляхи UI.
11. **Correlation ID** поєднує записи одного запиту між gateway і застосунками. Коректне вхідне значення зберігається, відсутнє або неправильне замінюється новим; воно передається далі в заголовку й повертається клієнту.

## ЛР1

1. **Автентифікація** встановлює, хто користувач; **авторизація** перевіряє, що йому дозволено. Видача токенів централізована в Auth, перевірка JWT і прав локальна в Auth, Catalog та Community.
2. **JWT** має header, payload і signature. Підпис дозволяє перевірити цілісність і довіреного видавця за налаштованим ключем. Payload — Base64url, а не шифрування: туди не можна класти пароль або секретний токен іншого сервісу.
3. **Catalog не викликає Auth для перевірки підпису:** йому достатньо налаштованих ключа/issuer/audience та перевірки строку дії. Звернення за metadata snapshot користувача в Community — інша задача; воно не є перевіркою підпису JWT.
4. **Різні ключі або audience** призводять до відхилення токена і 401. У наших процесах значення задаються спільною environment-конфігурацією, проте валідація відбувається незалежно.
5. **SHA-256 без солі** швидкий і дає однаковий результат для однакових паролів, що полегшує перебір і використання готових таблиць. Збережено оригінальний Identity PasswordHasher, який підтримує сольовий парольний хеш та його перевірку.
6. **Refresh** потрібен для нової короткоживучої access-сесії. Під час ротації старий refresh відкликається, створюється новий; у БД зберігаються хеші. Заміна та відкликання збережені транзакційно; рядок refresh блокується під час ротації. Повторне використання старого refresh дає 401.
7. **401:** немає чинного access-токена, наприклад POST catalog без Authorization або зі спливлим JWT. **403:** JWT чинний, але роль User не може створювати фільм; це перевіряє сам Catalog.
8. **DTO замість EF-сутності** відсікає password hash, навігації, цикли та службові поля і не дозволяє клієнту призначити собі роль чи середній рейтинг. Каталог має окремі DTO читання і create/update; старі UI-контракти залишені сумісними.
9. **Пагінація:** CountAsync обчислює кількість після фільтрів, OrderBy + стабільний Id задають порядок, Skip/Take обмежують сторінку. Клієнт отримує items, page, pageSize, totalCount; total залишено для старого frontend. Неправильні значення — 400, максимум pageSize — 100.
10. **Фільтрація в БД** не завантажує весь каталог у пам'ять застосунку. CatalogRepository будує IQueryable до ToArrayAsync; SQL можна побачити в debug-логах через ToQueryString. Інтеграційний тест перевіряє пошук, сторінку та наявність LIMIT у SQL.
11. **Своя БД сервісу** означає окремий connection string, контекст і міграції. Заборонено runtime JOIN/FK між базами та пряме підключення до чужої БД. Offline importer має тимчасовий доступ для переходу; він не є runtime-сервісом.
12. **Ocelot:** `DownstreamHostAndPorts`/scheme беруться з `Services:AuthUrl`, `CatalogUrl`, `MonolithUrl`; режим Services вмикає відповідних власників. Різні пріоритети захищають конкретні маршрути від catch-all. Для users окремо маршрутизуються me, адміністративний список і roles, щоб публічні рецензії/списки залишилися в Community.
13. **Шлях GET каталогу:** React → HTTP gateway 5000 → HTTP Catalog 5002 → SQL його cinemacity_catalog → DTO → gateway → React. Якщо передано JWT, Catalog перевіряє його локально; анонімне читання також дозволене.
14. **Старий каталог:** стан до переходу збережений у legacy. Після cutover його не змінюють як джерело істини. Community може оновлювати тільки свої reference-проєкції зі snapshot API; зміну назви/жанрів/складу виконує Catalog.

## Питання про зміну ціни вже замовленої позиції

У вихідному CinemaCity немає замовлень, продажу квитків або ціни: це каталог фільмів/серіалів із соціальними функціями. Додавати сторонній магазин для імітації цього прикладу означало б змінити предметну область. Item/Category адаптовані як Movie/Genre; решта залежностей походить із реального моноліту.

Загальний принцип для майбутнього платного сеансу або підписки: замовлення зберігає `priceAtPurchase`, валюту й потрібний опис позиції у своєму snapshot. Зміна поточної ціни Catalog застосовується до майбутніх замовлень, а не переписує вже підтверджену суму. На підтвердженні потрібно явно перевірити актуальну пропозицію/версію; зміни після підтвердження — окремий бізнес-процес, а не тихий перерахунок історії.

У нашому поточному домені аналогічна залежність — метадані фільму у старих списках і рецензіях. Вони містять стабільний MovieId; показ поточної назви використовує проєкцію Catalog, а самі оцінки/рецензії не переїжджають і не зникають при виділенні.
