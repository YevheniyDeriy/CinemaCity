# ЛР4: клієнт CinemaCity

Дата перевірки: 2026-11-02. Клієнт React використовує наявний дизайн, меню та тему CinemaCity. Моноліт і три його вихідні бібліотеки не редагувалися.

## Екрани

| Екран | Маршрут | API |
|---|---|---|
| Вхід / реєстрація | /auth | POST /api/auth/login, /register |
| Каталог | /catalog | GET /api/v1/catalog/items: search, page, pageSize |
| Деталі | /movies/:id | Один GET /api/v1/screens/movies/:id на спробу завантаження |
| Створення / зміна оцінки | /movies/:id/rate | GET /api/ratings, POST /api/ratings або PUT /api/ratings/:id |
| Мої операції | /my-ratings | GET /api/ratings, DELETE /api/ratings/:id |

У CinemaCity операція — оцінка. Поточна оцінка має серверний статус Active («Опубліковано»); скасування використовує наявне видалення оцінки, а не вигаданий стан бронювання. Новий GET /api/ratings повертає тільки оцінки поточного користувача. UserId береться з JWT. Публічне читання каталогу не потребує входу, персональний складений екран потребує.

## Один API-шар

`frontend/src/api/client.ts` містить конфігурацію адреси, HTTP, токен, refresh, дедлайн, помилки та cooldown. Усі попередні виклики fetch у main.tsx також переведені на цей шар. Інші компоненти не викликають fetch напряму.

- Base URL — VITE_API_URL; за відсутності конфігурації — gateway того самого hostname на 5000. Порожнє значення використовує same-origin proxy у Docker. Інші origins/сервісні адреси API-клієнт відхиляє.
- Access token зберігається в пам'яті. Відновлення після reload — через HttpOnly refresh cookie. У localStorage залишається лише налаштування теми.
- 401: одна спроба refresh, потім один повтор запиту. Паралельні 401 ділять один refresh-запит. Остаточний 401 скидає сесію і веде на вхід. Login/register не запускають refresh при невірних даних.
- 429: Retry-After розбирається як секунди або HTTP-date. До завершення очікування мережевих запитів відповідного бюджету немає, кнопка повтору показує час. Login має окремий cooldown від решти запитів.
- Gateway відкриває Retry-After, Location та X-Correlation-Id через CORS Expose-Headers: це необхідно для браузера на іншому порту.
- Мережа / timeout / 5xx: зрозумілий текст, без stack trace та назв винятків. Дедлайн клієнта 10 с, поточний gateway — 8 с, Community → власники — 5 с.
- ValidationProblemDetails.errors показуються біля відповідних полів. Для збережених legacy-відповідей оцінювання `{message}` є сумісне зіставлення відомих повідомлень із полем score/movieId.

## Форми та стани

Кожний новий екран розділяє loading, success, empty і error. Читання має AbortController та кнопку повтору; пошук — debounce 400 мс і скасування попереднього запиту. Каталог має серверну пагінацію. Часткова відповідь не перетворюється на «оцінки немає»: опис залишається, а персональний стан явно недоступний; створення з цього стану не пропонується.

У формі оцінки кнопка блокується, а синхронний ref додатково відхиляє подвійне натискання до React-render. Незмінне тіло після мережевої помилки повторно використовує той самий Idempotency-Key. Інше тіло — новий ключ. Одна спроба refresh теж зберігає тіло та ключ. Ключ скидається після підтвердженого успіху.

## Локальний запуск без робочих даних

У першому PowerShell 7 з E:\CinemaCity задайте CINEMACITY_TEST_POSTGRES зі своїм паролем. Демонстраційний стенд створює тільки власні тимчасові БД; вихід `exit` видаляє саме їх.

```powershell
$pgPassword = [System.Net.NetworkCredential]::new('', (Read-Host 'Пароль PostgreSQL' -AsSecureString)).Password
$env:CINEMACITY_TEST_POSTGRES = "Host=127.0.0.1;Port=5432;Username=postgres;Password=$pgPassword"
Remove-Variable pgPassword
$env:DOTNET_PROCESSOR_COUNT = '2'
dotnet build tools/CinemaCity.DefenseDemo -m:1 -p:UseSharedCompilation=false
dotnet tools/CinemaCity.DefenseDemo/.build/bin/Debug/net10.0/CinemaCity.DefenseDemo.dll
```

У другому вікні:

```powershell
cd E:\CinemaCity\frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Відкрити http://127.0.0.1:5173/catalog. Навчальні облікові записи стенд показує у своєму терміналі. Це демонстраційні, а не перенесені робочі дані з іншого ноутбука.

## Відтворення перевірок

```powershell
# У корені, CINEMACITY_TEST_POSTGRES заданий у цьому вікні:
dotnet test CinemaCity.slnx -m:1 -p:UseSharedCompilation=false

# У frontend:
npm test

# Стенд і Vite мають бути запущені, порожні навчальні оцінки:
npm run test:e2e
```

Браузерні сценарії використовують встановлений Microsoft Edge через Playwright. `smoke.cjs` перевіряє справжні сервіси: вхід, пошук/empty, один HTTP-запит деталей, створення, double click, мої оцінки, скасування та відновлення cookie-сесії. `failures.cjs` перевіряє керовані часткові/429/401/503-відповіді й незмінний ключ повтору. `pagination.cjs` додає тільки навчальні позиції каталогу, перевіряє дві сторінки, debounce, мобільну ширину та вихід, а потім прибирає створені ним позиції.

Окремий повільний функціональний fixture попередніх лабораторних має 15-секундний транспортний бюджет, щоб перше JIT/EF виконання на завантаженому ноутбуці не підміняло тест бізнес-поведінки тестом продуктивності. Gateway.Tests окремо перевіряє справжній timeout з 1-секундним бюджетом. У застосунку значення — 8 секунд; безмежного очікування немає.

## Контрольні питання

1. Один gateway приховує топологію сервісів та централізує транспортні правила.
2. Web-код публічний: JWT-ключів і паролів БД у ньому немає. Сервер отримує UserId із підписаного токена.
3. Клієнтська валідація дає швидкий зворотний зв'язок; серверна захищає дані від будь-якого клієнта.
4. Прострочений токен: один refresh і повтор; відмова refresh: вхід. 429: очікування Retry-After без нових запитів.
5. Empty — успішна відповідь без елементів; error — результат не вдалося отримати і пропонується повтор.
6. Тільки клієнт знає, що повтор після втраченої відповіді — та сама спроба. Новий серверний ключ зробив би її новою операцією.
7. Деталі — один складений запит. Повтор після явно показаної помилки є окремою спробою, а не трьома прихованими запитами екрана.
8. Legacy-помилки та різні `q`/`search` виявилися незручними. Канонічний клієнт використовує search; старі повідомлення оцінювання адаптуються до полів. Подальше вирівнювання всіх legacy-контрактів потребує явного версіонування, а не непомітного ламання baseline.
