# ЛР3: складений запит, автентифікація, кеш і ліміти

## Реалізація та демонстрація

Запустіть стек через `scripts/Start-Local.ps1 -Mode Services`, або `docker compose up --build` після підготовки джерела та .env. Єдина зовнішня точка API — http://localhost:5000. Swagger шлюзу: http://localhost:5000/swagger; контракт: /openapi/gateway.json.

Отримайте accessToken через POST /api/auth/login, потім:

```http
GET http://localhost:5000/api/v1/screens/movies/{{movieId}}
Authorization: Bearer {{accessToken}}
X-Correlation-Id: lab3-demo
```

Шлюз паралельно звертається до Catalog `/api/v1/catalog/items/{id}` та Community `/api/profile/movies/{id}/state`. DTO екрану належить шлюзу: movie (id, title, releaseYear, posterUrl), myState (watchlistStatus, myScore, lists), partial, communityStatus. Жодні суми, знижки або правила створення оцінок у шлюзі не обчислюються. UserId не приймається від клієнта: Community отримує початковий JWT після перевірки шлюзом.

Якщо Catalog не знайшов фільм — 404; при його недоступності — 503; при timeout — 504 ProblemDetails. Якщо недоступний лише Community, повертається 200 з partial=true, myState=null та communityStatus=unavailable/timeout. Відсутня операція у доступному сервісі відрізняється станом available. Складена відповідь має Cache-Control: no-store.

## JWT та мережа

JWT перевіряється на вході: підпис, issuer, audience, строк дії. JWT Secret береться лише зі змінних середовища або ігнорованого .env; у шлюзу ті самі issuer/audience/secret, що в Auth. Некоректний або відсутній токен для захищеного запиту повертає 401 ProblemDetails до будь-якого downstream-виклику. Реєстрація, login/refresh/Google callback та загальнодоступне читання залишаються доступними за старими маршрутами. Авторизаційні бізнес-правила й ролі перевіряє власник даних.

Шлюз видаляє клієнтські X-User-Id/X-User-Roles. Передається оригінальний JWT, а не довірені заголовки. Сервіси зберігають власну перевірку JWT як додатковий захист та сумісність із ЛР1/ЛР2; код моноліту не змінювався. Це свідоме рішення: не вимикати захист сервісів заради економії однієї локальної криптографічної перевірки.

У Docker у Auth/Catalog/Community немає ports, тільки expose всередині мережі Compose. З хоста порти 5001/5002/5003 не публікуються. Діагностичний локальний PowerShell-режим прив'язує сервіси до localhost; він не є мережевою ізоляцією від інших процесів того самого комп'ютера. Для демонстрації недоступності прямих портів використовуйте Docker-режим без паралельних локальних процесів. Docker-оточення раніше мало помилку read-only filesystem; запуск контейнерів у цій сесії не підтверджувався.

## Кеш

IMemoryCache з TTL 60 секунд містить тільки успішно отримані публічні деталі фільму для складеного екрана. Звичайні проксовані GET не кешуються: їхня статистика оцінок має залишатися свіжою як у ЛР2. Catalog-виклик для кешу не містить Authorization, Cookie або X-User-Id. Ключ: покоління каталогу + канонічний downstream path з UUID фільму. Складений екран не має фільтрів або пагінації, тому query клієнта не впливає на запит деталей. При додаванні кешування списків до ключа слід включити всі параметри фільтрів/сортування/пагінації. Персональні myState, профілі, операції та складені відповіді не кешуються. TTL обмежує застарілість після змін в обхід шлюзу.

Після успішного POST/PUT/PATCH/DELETE каталогу через gateway збільшується покоління кешу. Це відбувається у downstream handler до відправлення відповіді клієнту. Інвалідизуються всі кешовані описи фільмів після запису через будь-який catalog/admin alias. Якщо старий GET ще виконується, він запише результат у старе покоління, яке нові запити вже не читають. Невдала зміна не скидає кеш.

## Частота та дедлайни

Fixed window, черга вимкнена:

| Група | Ключ | Ліміт |
|---|---|---|
| Анонім | реальна IP-адреса TCP-з'єднання | 120/хв |
| Авторизований | sub JWT | 240/хв |
| Login (обидва alias) | IP-адреса | 5/хв |

429 має Retry-After у секундах та ProblemDetails. X-Forwarded-For від клієнта не використовується для обходу ліміту. Ліміти налаштовуються Gateway__Limits__anonymous, Gateway__Limits__user, Gateway__Limits__login та Gateway__Limits__WindowSeconds.

Усі HTTP-виклики мають дедлайн Gateway__TimeoutSeconds (3 секунди). Це стосується named clients композиції/readiness та Ocelot handler. Проксовані збої Ocelot зберігають контракт 503; складений запит розрізняє 503 і 504. Передається CancellationToken і X-Correlation-Id. Повторів для POST немає. /health — liveness; /health/ready паралельно перевіряє Auth/Catalog/Community, повертає 200 або 503 з переліком станів.

## Перевірки

Новий проєкт CinemaCity.Gateway.Tests використовує справжній gateway через WebApplicationFactory та HTTP-стаби на Kestrel. Перевіряються повна відповідь і паралельність, часткова відповідь при відмові Community, 401 без downstream-викликів, cache hit та ізоляція двох користувачів, інвалідизація після PUT, жорсткіший login-ліміт із Retry-After і timeout Catalog. Повний набір старих тестів також запускається. Спільний fixture попередніх лабораторних має підвищений login-ліміт через численні повторні логіни; політики лімітів перевіряються окремими ізольованими Gateway.Tests.

Єдина очікувана зміна попереднього baseline: gateway тепер повертає 401 у форматі ProblemDetails відповідно до ЛР3. Статуси та бізнес-відповіді сервісів не змінювалися. Моноліт і його вихідні бібліотеки перевіряються за docs/monolith-sha256.json.

## Контрольні питання

1. Gateway маршрутизує, автентифікує, складає DTO екрана, кешує спільне та обмежує частоту; оцінки й доступ до чужих списків визначає Community.
2. Розрахунок рейтингу належить Community/Catalog, а не шлюзу: інакше правила дублюватимуться.
3. Паралельні виклики дають приблизно max(Tcatalog,Tcommunity), а послідовні — їх суму.
4. Без дедлайну завислі запити накопичують ресурси шлюзу; дедлайн обмежує час очікування.
5. null з unavailable означає збій; null за available може означати відсутність оцінки. Це різні стани екрана.
6. Перевірка JWT на вході відсікає неавтентифікований трафік. Довіряти X-User-Id можна лише від захищеного шлюзу в ізольованій мережі; тому тут обрано передачу JWT та видалення сторонніх identity-заголовків.
7. Кешуються лише відповіді Catalog без облікових даних. Кешування профілю чи всієї композиції могло б віддати дані іншої людини.
8. Канонічний path з UUID задає об’єкт; покоління задає інвалідизацію. TTL 60 с знижує навантаження і обмежує застарілість.
9. Без інвалідизації навіть після успішного редагування клієнт бачив би стару назву до завершення TTL.
10. Fixed window рахує N запитів у вікні й допускає сплеск на межі; token bucket поступово поповнює жетони. Для лабораторної обрано простий fixed window.
11. До входу стабільного userId немає, тому використовується IP. Після входу ліміт за sub не змішує різних користувачів за NAT.
